# AGENTS.md

This file provides guidance to every coding agent when working with code in this repository. CLAUDE.md points here; every coding agent reads this file first.

## Project status

A WPF app that imports bank-transaction Excel sheets into SQL Server (2012 or newer) or a local SQLite file and searches them. Two screens work: Import and Query. The Import screen (MVVM, CommunityToolkit.Mvvm): `MainWindow` is a shell with a left nav list (Import and Query) and a ContentControl bound to `CurrentViewModel`; `ImportViewModel` (states Idle/Staging/Preview/Committing/Done) drives choose file, progress/cancel, a five-tab paged preview, commit, discard (with a confirmation) and close handling. ViewModels are in `src/ExcelSearch/ViewModels`, Views in `Views`, the shared look (palette, fonts, banded `LedgerGrid`, buttons) in `Themes/Theme.xaml`, logo/icon files in `Assets/` (the original logo stays in the repo root), and they depend only on interfaces (`IImportPreviewService`, `IInvalidRowExporter`, `ITransactionQueryService`, `IDialogService`), so tests use fakes. `ExcelSearch.Core/Import` holds a streaming Excel parser (ExcelDataReader, xlsx only) that yields normalized, validated rows lazily; `ExcelSearch.Tests` (xUnit, net8.0-windows so it can reference the WPF project) covers it. `ExcelSearch.Core/Staging` (`IStagingStore`, `ImportPreviewService`) and `ExcelSearch.Data/SqlServerStagingStore` stage a parsed file into `ImportStaging` and classify it in SQL. `CommitAsync` (same store) writes a staged batch into `Transactions` in one transaction under the `ExcelSearch.Commit` application lock, then deletes its staging rows; `DiscardAsync` first flips a `Staged` batch to `Discarded` (refusing committed/discarded ones) and commit holds an UPDLOCK on the batch row, so the two cannot race; the commit lock wait is the `CommitLockTimeoutSeconds` setting (default 120). The database runs with READ_COMMITTED_SNAPSHOT on (`Scripts/db/004_enable_rcsi.sql`). `CleanupStaleBatchesAsync` runs at startup. The Conflict tab shows what differs from the database row (`GetConflictPageAsync`, `ConflictDiff`); the Conflicts tab has a per-row Overwrite checkbox (saved immediately via `SetConflictOverwriteAsync`) plus Overwrite all / Skip all and a database-read count; `RefreshAgainstDatabaseAsync` re-compares New / Already-in-database / Conflict rows with `Transactions` under the batch-row lock; `InvalidRowExporter` writes the Invalid rows (original cell values + Source Row + Errors) with the forward-only `StreamingXlsxWriter` (MiniExcel was tried and removed: it buffers the whole sheet in memory). `ErrorCellScanner` finds Excel error values (`#DIV/0!`) that ExcelDataReader reports as null. Sample workbooks (including `10_query_demo_3000_rows.xlsx` for the Query screen, with a manual checklist in `Samples/test/README.md`) are generated into `Samples/test/` by `Scripts/samples/make_samples.py`. The Query screen (a collapsible filter drawer, removable filter chips, a column picker, row details that open under the selected row, one slim totals/paging bar; `QueryViewModel`/`QueryView`, `Core/Query`, `Data/SqlTransactionQueryService`) searches `Transactions`: `TransactionFilter` (provider-agnostic, `Normalized()` trims and strips the CNIC to digits) is turned into one parameterized LINQ query; sorting goes through the `TransactionColumn` whitelist (all 30 grid columns sort; narrations are unindexed) with an `Id` tie-break; page, count and totals are separate queries (the grid shows before the count arrives); the dropdown values are cached in the service and dropped when the Import screen sends `ImportCommittedMessage` (messenger, no direct dependency between the screens); export streams keyset chunks of 10,000 into `StreamingXlsxWriter` or a CSV (xlsx refused above 1,048,575 rows) and writes either the columns ticked in the Columns picker (default) or all 30 fields, chosen from a fixed name table in `TransactionExportWriter`. `Scripts/db/005_query_indexes.sql` is a DRAFT of proposed indexes and has not been applied. The database engine can be switched in the app (the **Database** selector at the bottom of the left rail, SQL Server / "Local DB"; `ShellViewModel` saves the choice with `UserSettings` to `%LocalAppData%\ExcelSearch\user-settings.json`, a configuration source that overrides appsettings, and restarts the app through `IAppLifecycle`) or by configuration (`Database:Provider` = `SqlServer` (default) or `Sqlite`, plus `Database:SqlitePath`, default `%LocalAppData%\ExcelSearch\excelsearch.db`; a restart switches it): `ExcelSearch.Data` has `SqlServer/` (the SQL Server staging store and query service) and `Sqlite/` folders, `AddExcelSearchDatabase` registers the context factory, `IStagingStore` and `ITransactionQueryService` for the chosen provider, and `StagingStoreBase` holds the EF-only store methods both stores share. SQLite mode runs the whole Import pipeline (`SqliteStagingStore`: one transaction + a prepared INSERT to load, set-based SQL to classify/re-check, `BEGIN IMMEDIATE` instead of the application lock to commit); the Query screen works on both providers: `TransactionQueryServiceBase` holds the shared search (filter to LINQ, sort whitelist, totals, keyset export) and `SqlTransactionQueryService` / `SqliteTransactionQueryService` override only text matching (SQLite: `EF.Functions.Like` with an ESCAPE character, because EF's `Contains` is case-sensitive there; money filters, ORDER BY and SUM run in SQL on the integer cents), text ordering (`COLLATE NOCASE`), multi-select lists (`COLLATE NOCASE`) and timeout detection. The customer-name filter has a Contains / Starts-with toggle (`TransactionFilter.CustomerNameMode`, default Contains; shown in the chip), and the CSV save choice carries `ExportNotes.CsvLeadingZeros`. SQLite stores money as INTEGER cents, timestamps as ISO UTC text and key columns `COLLATE NOCASE`; the type mapping and every difference from SQL Server are in `db.md`. There is no linter.

Bank-statement sheets WITHOUT pay order no / txn ref (most cash deposits) are supported: `Transactions.Id` is the primary key, those two fields are optional, duplicates of key-less rows are flagged on the preview ("Already in database", "Repeated in file", "Possible duplicates") and imported unless the user ticks "Skip flagged duplicates"; `NarrationExtractor` derives `SlipNo` (Narration 1, only for rows without a Txn Ref), `NarrationCnic` (Narrations 2-5) and, when the Br. Code column is empty, `BranchCode` (from `/Br: nnnn`, UBL statements) for searching and for the Possible-duplicate hint. Rows that have both fields keep the old Conflict / Overwrite rules. Cash/bank rows are recognised in tiers (Txn Ref + bank + account for UBL-style rows; slip no., then date + amount + branch code for HBL-style cash rows, with `ImportStaging.MatchReason` 1/2/3 saying why, shown as the "Why flagged" column): `Docs/KeylessImport.md` > Cash rows. What the app did before, why it changed and how to revert it: `Docs/KeylessImport.md`.

New to the repo? Start with `Docs/quickstart.md` (development setup: requirements, checks, first run).

## Commands

```
dotnet build ExcelSearch.sln
dotnet run --project src/ExcelSearch
dotnet test src/ExcelSearch.Tests --filter "Category!=Integration&Category!=Large"   # Unit: run this while developing
dotnet test src/ExcelSearch.Tests --filter "Category=Integration&Category!=Large"    # Integration: run before a commit (needs EXCELSEARCH_TEST_CONNECTION, the SQL Server dev database)
EXCELSEARCH_RUN_LARGE=1 dotnet test src/ExcelSearch.Tests --filter "Category=Large"  # Large: on demand (200,000 / 500,000 rows)
dotnet test src/ExcelSearch.Tests                                                    # everything except Large (Large tests skip themselves)
```

Test tiers are xUnit traits: **Unit** is the default (no trait; no database, or a temp SQLite file, so the SQLite halves of the contract tests are Unit), **Integration** (`[Trait("Category","Integration")]`) needs the SQL Server development database named by the environment variable `EXCELSEARCH_TEST_CONNECTION` (unset: the tests skip), **Large** is also opt-in by `EXCELSEARCH_RUN_LARGE=1`. Roughly 265 Unit tests in 11 s, 79 Integration tests in 20-30 s. xUnit runs test CLASSES in parallel, including the SQL Server ones (they do not share rows: every test uses its own `TEST_<guid>` keys); running them serially (`-- xUnit.ParallelizeTestCollections=false`) takes about 19 s instead of 11 s for that tier.

### Testing policy
- Test behaviour and risks, not every property. One test per behaviour; use `[Theory]` for variations of the same rule.
- Share expensive setup (a database file, a seeded batch) with class fixtures instead of rebuilding it per test.
- No new tests for pure UI plumbing (visibility, banners, button enablement, selection resets). Keep ViewModel tests for logic that talks to a service or decides something.
- A new feature gets a small, focused set: its main path, its riskiest edge, and its failure reason. Do not restate another test's assertions.
- Anything that must behave the same on SQL Server and SQLite is written once as a contract test (`*Contract.cs`) and run by both shells in `ContractTestShells.cs`; add a provider-specific test only for what is genuinely different.
- Do not delete a test that is the only coverage of a risky behaviour (commit guards and failure reasons, the discard/commit race, re-check, overwrite rules, classification, parser rules, export round trips, money/collation/schema on SQLite).

Database tests run against the single development database named by `EXCELSEARCH_TEST_CONNECTION`. That variable is the ONLY source: the tests never read the app configuration (production config will point at a real server), skip when it is unset, and fail with a refusal when the database name contains "prod" (case-insensitive); `TestDatabase` in `StagingTestSupport.cs` enforces this. Every test uses unique `TEST_<guid>` keys and deletes only the rows it created (never truncate or reseed). The store behaviour tests are CONTRACT tests (`*Contract.cs`, abstract) run on both providers through the shells in `ContractTestShells.cs`: `*_SqlServer` use the development database, `*_Sqlite` use a fresh temp file per test class (`SqliteDatabaseFixture`, deleted afterwards) and are not affected by `EXCELSEARCH_SKIP_DB_TESTS`; `SqliteSpecificTests` covers cents, case-insensitive keys, the schema initializer and the connection settings. Set `EXCELSEARCH_SKIP_DB_TESTS=1` to skip the SQL Server ones; the 200,000-row tests and `QueryLargeContract` (500,000 rows, both providers) also need `EXCELSEARCH_RUN_LARGE=1`. Query tests scope every search to their own import batch, so real rows never leak into a result.

Re-scaffold the EF model after a schema change (generated code is not hand-edited; use your real connection string):

```
dotnet ef dbcontext scaffold "<connection string>" Microsoft.EntityFrameworkCore.SqlServer --project src/ExcelSearch.Data --startup-project src/ExcelSearch --context AppDbContext --context-dir . --output-dir Entities --namespace ExcelSearch.Data.Entities --context-namespace ExcelSearch.Data --table dbo.ImportBatches --table dbo.Transactions --table dbo.ImportStaging --no-onconfiguring --force
```

`dotnet-ef` is installed as a global tool. Pass the connection string on the command line: the WPF project's host config is not available to `dotnet ef` at design time.

## Architecture

- `src/ExcelSearch` (net8.0-windows, WPF) references `ExcelSearch.Core` and `ExcelSearch.Data` (both net8.0). Core and Data must never reference the WPF project.
- Startup is in `App.xaml.cs`, not `StartupUri`: it builds a generic host, registers the context factory, parser, staging store and `MainWindow` in DI, and shows the window from the host. Windows get their dependencies by constructor injection.
- `AppDbContext` is registered through `AddDbContextFactory` (a singleton factory); consumers inject `IDbContextFactory<AppDbContext>` and create a short-lived context per operation. Do not inject a scoped `AppDbContext` into windows: the Development environment validates scopes and the app would crash on startup.
- `ExcelSearch.Data` holds the scaffolded output (`AppDbContext.cs`, `Entities/`, SQL Server mapping) plus hand-written code in `SqlServer/`, `Sqlite/` and the shared root files. Add customisations through the generated partial hooks (`OnModelCreatingPartial` is implemented in `AppDbContext.Partial.cs` and applies `Sqlite/SqliteModelConfiguration` when the context runs on SQLite; `partial class` entities), or they are lost on the next `--force` scaffold. Core must stay provider-free; only `ExcelSearch.Data` knows about SQL Server or SQLite.
- EF Core and Hosting package versions must stay on the 8.x line to match the target framework.
- **SQL Server 2012 must keep working** (the production server is 2012 Express): no `STRING_AGG`, `OPENJSON`, `DROP ... IF EXISTS`, `CREATE OR ALTER` or inline `INDEX` inside `CREATE TABLE` in any script or raw SQL. `AddExcelSearchDatabase` sets `UseCompatibilityLevel(110)`, under which EF writes `Contains` lists as constants, so multi-select filters are built as ORed parameters (`AnyOfCore`) to stay parameterized. Run the Integration tier against the 2012 server too when the SQL changes.

## Configuration

- Connection string key: `ConnectionStrings:DefaultConnection` (SQL Server only; one `sa` connection string shared by all copies of the app). Sources, last wins: `appsettings.json`, `appsettings.{Environment}.json`, environment variables, command line, then `%LocalAppData%\ExcelSearch\user-settings.json` (the in-app database choice). No user secrets are used. Provider keys: `Database:Provider` (`SqlServer` | `Sqlite`, default `SqlServer`) and `Database:SqlitePath` (environment variables such as `%LocalAppData%` are expanded; the folder is created). `appsettings.Sqlite.json.example` shows the SQLite setting.
- `appsettings.json` is committed with an empty value. `appsettings.Development.json` and `appsettings.Production.json` hold real credentials and are **gitignored**; the committed `*.json.example` files and `appsettings.Production.sample.json` are templates. Never commit the real ones. Debug builds are forced to Development, Release builds (including the published package) to Production, whatever `DOTNET_ENVIRONMENT` says. `appsettings.Production.json` is copied to the build and publish output; `appsettings.Development.json` only for Debug; the sample never. A missing or failing SQL Server connection shows a dialog naming the file and key (`SqlServerConnectionCheck`), and the window stays open so Local DB can be chosen. The default SQLite path stays `%LocalAppData%\ExcelSearch\excelsearch.db`: keep `Database:SqlitePath` empty in the committed files.
- Deployment: `Scripts/publish.ps1` makes a framework-dependent win-x64 package in `publish/` (version and file properties are in `ExcelSearch.csproj`; `RollForward=LatestMajor`). To use the real production connection string, edit the one value in `appsettings.Production.json` and run the script. See `Docs/Deployment.md`.
- `App.xaml.cs` forces the `Development` environment under `#if DEBUG`; other builds default to `Production`. Local development uses SQL Server Express (`.\SQLEXPRESS`, database `ExcelSearch`) with the credentials in `appsettings.Development.json`; `appsettings.Production.json` points at the production SQL Server 2012 Express on the LAN (database `AuditExcel`).

## Database

`Scripts/db/001_create_tables.sql` plus the later numbered scripts (002-004, 006, 007) are the source of truth for the schema (each re-runnable; 001 creates tables only if missing and still shows the ORIGINAL business-key design, which 006 replaced). `Scripts/db/init_db.sql` joins 001-004, 006 and 007 (create database if missing, tables, staging, concurrency columns, RCSI, surrogate key, cash matching) into one re-runnable script for building a fresh database; 005 is a draft and is not in it. Keep it in step with the numbered scripts. Performance numbers and what each change bought are in `Docs/Performance.md`. `db.md` documents the live schema and keeps a dated change history. Keep the script, the scaffolded model and `db.md` in sync, and follow `db.md`'s maintenance rules (bump its Version and Last Updated, add a dated note for every change, mark removed tables `[REMOVED]` rather than deleting them).

Design decisions that code must respect:
- `Transactions.Id` (GUID, column default `newsequentialid()`, left out of the commit insert) is the clustered PRIMARY KEY since 2026-10-14. `PayOrderNo` and `TxnRefSeqNo` are optional: rows that have BOTH stay unique through the filtered unique index `UX_Transactions_Key` (a duplicate is still error 2627); rows without them may repeat. A row with only one of the two counts as key-less. Never sort, page or look a row up by the pair: use `Id` (`TransactionKey` is the Id; the sort tie-break and the export keyset are `Id`).
- `RowHash` (SHA-256 hex of the normalized business columns; not `SlipNo` / `NarrationCnic`) drives import behaviour. Rows with a full key: same key and same hash is an exact duplicate (skip); same key and different hash is a conflict (user decides). Key-less rows: same hash in the database = Already in database, identical earlier row in the file = Repeated in file; Possible duplicate (status 6, reason in `ImportStaging.MatchReason`) = (1) same slip no + date + account + amounts, (2) same date + amount + branch code + bank unless both rows have different slip numbers (database rows only, never within the file), or (3) a row with a Txn Ref whose Txn Ref + bank + account exists with other values (a row with a Txn Ref is never matched by date and amount); all are FLAGGED, never blocked, and committed unless `CommitAsync(skipFlaggedDuplicates: true)`. `ImportBatches` counters (`NewRows` = every row written, `SkippedRows` = every valid row left out, `UpdatedRows`, `RejectedRows`) mirror those outcomes. The classification rule exists twice, as SQL (`SqlServer/StatusSql.cs`, `Sqlite/SqliteStatusSql.cs`, shared by classify and re-check); change both together.
- Identifiers (CNIC, account numbers, references) are text, not numbers, so leading zeros survive; `Cnic` is stored digits-only. Amounts are `decimal(18,2)`.
- The database collation is case-insensitive, so keys differing only by case collide. (SQLite: `COLLATE NOCASE` on `PayOrderNo`/`TxnRefSeqNo` everywhere they appear, ASCII only.)
- SQLite schema: `Scripts/db/sqlite/001_create_schema.sql`, `002_surrogate_key.sql` (a table REBUILD) and `003_cash_matching.sql` are embedded in `ExcelSearch.Data` and applied by `SqliteSchemaInitializer` (version in `PRAGMA user_version`; a newer file is refused). The SQL Server twins are `Scripts/db/006_surrogate_key.sql` (of 002) and `007_cash_matching.sql` (of 003: Br. Code to 50 characters, `ImportStaging.MatchReason`, `IX_Transactions_Match`); each has a tested rollback in `Scripts/db/rollback/`. A schema change means: the SQL Server script(s) and `init_db.sql`, a NEW numbered SQLite script (never edit a released one), the entities/model, and `db.md`, together.
- SQLite money columns hold integer cents behind an EF converter. Never compare or sum them as text, and anything written by hand in SQL uses cents. EF's `Contains` is `instr()` there (case-sensitive): use `EF.Functions.Like` for text search on SQLite.
- Never put the SQLite file on a network share or synced folder. `Microsoft.Data.Sqlite` pools connections: call `SqliteConnection.ClearAllPools()` before deleting a database file.
- Some source Excel headers are misspelled (`Delear Name`, `Narraction 1`); the header-to-column mapping is in `db.md` and the script header.

## Environment gotchas

- The repo path contains `[D]` (`D:\Ry Work [D]\...`). PowerShell cmdlets treat brackets as wildcards, so `Start-Process -WorkingDirectory` and non-literal `-Path` arguments fail on it. Use `-LiteralPath` or .NET APIs (`System.Diagnostics.Process`).
- `publish/` is the output of `Scripts/publish.ps1` (gitignored); it contains `appsettings.Production.json` with the password, so never copy it into git or share it.
- `sqlcmd` is available for queries. Use `-C` to trust the server certificate. The production server negotiates TLS 1.0 (original SQL Server 2012 release), so the driver prints a security warning; a bulk load over that LAN link is about 7x slower than the local dev server and once dropped its connection (`Docs/Performance.md` section 12).
- `Samples/software filed*.xlsx` are real bank data: git-ignored, never commit or paste their contents.
- The WPF app can be driven headlessly with UI Automation (controls have `AutomationId`s such as `ChooseFileButton`, `CommitButton`, `DiscardButton`, `RowsGrid`). The OpenFileDialog and message boxes cannot be driven that way.
